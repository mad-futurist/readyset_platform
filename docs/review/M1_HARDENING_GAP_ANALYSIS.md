# M1 hardening gap analysis

## Method and evidence

This review treats documentation as a claim set and the tracked implementation as the source of evidence. It inspected all production Python and TypeScript source, the generated OpenAPI snapshot and client declarations, Alembic history, tests, ignore rules, dependency manifests, Docker files, Compose, CI, architecture/ADR/research documents, and repository status. `demo/` and `references/` were not executed, imported, or modified.

Repository evidence on 2026-09-18:

- `git check-ignore -v apps/web/src/lib/api.ts` and the corresponding contracts/tests resolve to the root `.gitignore` pattern `lib/`.
- `git ls-files` therefore omits the frontend API layer and all current Vitest files.
- GitHub Actions run `35334487033` for commit `18e5342` failed. Its web annotations report missing `@/lib/api` followed by strict-TypeScript inference errors. The API job had no reported code failure.
- The only Alembic revision is the already-published initial revision `d24151675ee0`; corrections must be additive.
- Backend tests use SQLite only. CI provides PostgreSQL for migration checks but does not run marked PostgreSQL integrity/concurrency tests.

## Implementation order

1. Repair ignore rules and make the current web source/tests trackable.
2. Add deterministic contract export and CI drift checks.
3. Add configuration/email foundations and corrective database migration.
4. Harden registration, login, identity-bound sessions, OAuth, linking, reset, and invitations.
5. Add owner transfer, relational integrity, PATCH validation, typed pagination, and version locking.
6. Add frontend and PostgreSQL integration coverage.
7. Reconcile all architecture, security, database, API, deployment, and developer documentation.
8. Run clean-install/build, backend unit/integration, migration, generated-artifact, ignore/isolation, and production-config validation gates.

## Implementation outcome

All non-deferred findings above are implemented in this change set. The two explicitly deferred items remain deferred with their documented controls: PostgreSQL RLS is not an M1 feature, and direct signed transfer/malware inspection is not falsely claimed. Local unit and web gates pass; the three PostgreSQL-specific tests are wired into CI and require either Docker/Compose or the CI PostgreSQL service for execution. The final verification record belongs in the task handoff rather than rewriting the evidence captured at analysis time.
